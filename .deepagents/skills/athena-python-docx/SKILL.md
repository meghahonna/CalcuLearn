# athena-python-docx

Athena's drop-in `python-docx` replacement. Imports look identical (`from docx import Document`), but every paragraph, run, and table mutation flushes through DOCX Studio into the same Keryx Y.Doc that Olympus's `SuperDocumentYjsRendererCore` is bound to — so collaborators see edits land live, comments and presence stay attributed, and there is no export-and-swap step.

## Setup

```bash
pip install athena-python-docx           # 0.5.0+
export ATHENA_DOCX_BASE_URL=https://docx-studio.stg.athenaintel.com  # or prod
export ATHENA_DOCX_API_KEY=<your Athena API key>
```

In the Daytona computer-asset sandbox both vars are injected directly into the process env at `/initialize` time, so any subprocess (`langgraph dev`, terminals, ad-hoc Python execs) inherits them automatically — you don't need to set them yourself.

That's it. The SDK is pure-Python — every primitive (`add_paragraph`, `add_table`, `paragraph.text = "..."`, etc.) lands as a typed command on docx-studio's `POST /docs/:id/commands`. The server holds the Superdoc/Keryx session; the client carries no binary, no `superdoc-sdk`, no embedded CLI.

### What changed in 0.5.0 (vs 0.4.x)

If you're updating from 0.4.x, three things matter at the surface:

- **`Document.save(path_or_stream)` is now required.** Calling `save()` with no argument raises `TypeError`, matching upstream python-docx. The argument is accepted but ignored at runtime (Athena docs are always saved in-place against the Y.Doc). Use the context manager (`with Document(...) as doc:`) for auto-flush at the end of a block, or call `docx.flush_all()` to drain everything.
- **`transport="direct"` removed.** The legacy embedded-Superdoc path is gone; HTTP is the only transport. Drop any `transport=` kwarg from existing code — it'll raise `TypeError`. Pods no longer need `SUPERDOC_COLLAB_TOKEN` / `KERYX_WS_URL` env vars at all.
- **Typed command bus + buffered transport.** All primitives go through a `CommandBuffer` that batches pure mutations on a 100ms idle window and flushes eagerly for queries / response-bearing creates. This is invisible at the call site — but it means consecutive setters (e.g. `r.bold=True; r.italic=True; r.underline=True`) can land in one HTTP request instead of three. `requests.Session` carries a status-only retry strategy (3 × 0.5s backoff on 429/502/503/504) so transient server hiccups don't corrupt your batch.

## Entry points

| You have | Use | Status |
|---|---|---|
| An existing SuperDocument asset (`asset_<uuid>`) on **yhub** | `Document("asset_…")` | ✅ HTTP transport |
| Nothing — start blank | `Document.create(name="…")` | ✅ Creates asset + opens via HTTP |
| A SuperDocument asset on **ysweet** | — | ❌ raises `UnsupportedProviderError`; migrate first |
| A local `.docx` template | — | ❌ Phase 2+; create the asset first, then edit |

`base_url` and `api_key` fall back to `ATHENA_DOCX_BASE_URL` / `ATHENA_DOCX_API_KEY` env vars, so most call sites need no kwargs at all.

```python
# Net-new — most common SDK callsite
doc = Document.create(
    name="Q1 Report",
    base_url="https://docx-studio.stg.athenaintel.com",
    api_key=os.environ["ATHENA_DOCX_API_KEY"],
)
# `doc` is already opened against Keryx — no env vars needed.
doc.add_heading("Q1 Report", level=1)
doc.add_paragraph("Generated by Athena.")

# Open existing — Daytona-style
doc = Document("asset_<uuid>")  # reads ATHENA_DOCX_BASE_URL / ATHENA_DOCX_API_KEY from env
```

`Document.create()` is the only entry point that **deviates** from python-docx; it's a separate factory because we can't fabricate a SuperDocument asset client-side. See `python-sdk/CLAUDE.md` for the parity rationale.

## Default workflow: append, edit, save

The doc you're handed already has a style table, theme, and (usually) some content. **Treat the doc as a flow you can append to or edit in place.** Don't rebuild the styles, don't dump XML — let the Word style table and the user's existing content do the heavy lifting.

The full pattern lives in `references/template-workflow.md`. The five-step summary:

1. **Inspect** — walk `doc.paragraphs`, `doc.tables`, log style names and text. Or use `doc.iter_inner_content()` to walk paragraphs and tables together in document order. (Run `scripts/inspect_doc.py asset_<uuid>` to do this in one shot.)
2. **Append** with `doc.add_heading(text, level=N)`, `doc.add_paragraph(text, style="...")`, `doc.add_table(rows, cols)`. Or **insert before** an existing paragraph with `paragraph.insert_paragraph_before(text)`.
3. **Edit** by assigning to `paragraph.text` (replaces the paragraph's content) or by walking `paragraph.runs` and assigning to `run.text`. Use `paragraph.style = "Heading 2"` to change a paragraph's style.
4. **Format** runs via `run.bold = True`, `run.font.size = Pt(11)`, `run.font.color.rgb = RGBColor(0x1F, 0x49, 0x7D)`, etc. **Inside body paragraphs, prefer style names** (e.g. `paragraph.style = "Heading 1"`) over per-run font overrides — let the Word style table decide sizes and colors so the doc stays on-brand.
5. **Save** — `doc.save("anything.docx")` flushes the buffer to Keryx; the path argument is required for python-docx parity but ignored at runtime. **The recommended pattern is the context manager**: `with Document(...) as doc:` autosaves on clean exit and always closes the session. From the Daytona prelude, call `docx.flush_all()` to drain every live `Document` instance in the process — it's a no-op when nothing is open.

## Writing text — the safe pattern

```python
p = doc.add_paragraph("First paragraph.")          # text + default Normal style
p2 = doc.add_paragraph("Second paragraph, styled.", style="Body Text")
p2.alignment = WD_ALIGN_PARAGRAPH.JUSTIFY

# Add a run with custom formatting on top of an existing paragraph
r = p.add_run(" Important.")
r.bold = True
r.font.color.rgb = RGBColor(0xC0, 0x00, 0x00)
```

**Avoid** `paragraph.clear()` followed by a loop of `add_run()` immediately after creating the paragraph — Superdoc's commit pipeline can race against `getNodeById` and raise `Block X was not found`. Instead, pass the text into `add_paragraph(text, ...)` directly, then `add_run()` for any *additional* spans. The same offset-handling fix that landed in SDK 0.1.8 keeps run order correct on plain `add_run()` calls; the 0.5.0 fix to `Run.add_break` extends the same bookkeeping to `r.add_break()` followed by `r.add_text(...)`.

**Avoid** setting `font.size` / `font.name` on runs that live inside a styled paragraph (Heading 1, Title, Body Text) — the Word style table already specifies them, and overriding per-run produces drift between the style and the rendered text. For ad-hoc emphasis (a single bold word, a colored callout span) per-run formatting is the right call.

## Tables

```python
tbl = doc.add_table(rows=3, cols=4, style="Light Grid Accent 1")
tbl.cell(0, 0).text = "Region"
tbl.cell(0, 1).text = "Q1"
# ...
new_row = tbl.add_row()             # appends below the last row
new_col = tbl.add_column()          # appends to the right; pass width=Inches(1.2) to size it

# 0.5.0+: convenience accessors that mirror python-docx exactly
header_cells = tbl.row_cells(0)        # list of cells in row 0
first_col = tbl.column_cells(0)        # list of cells in column 0
parent = tbl.table                     # self-reference for symmetric block walking

# Merged cells: every grid position inside a merge resolves to the master,
# so cell(0,0).text == cell(0,1).text == cell(0,2).text after merging the
# top row. This matches python-docx semantics; previous versions returned
# empty strings for the non-master positions.
tbl.cell(0, 0).merge(tbl.cell(0, 2))
tbl.cell(0, 0).text = "Header"
assert tbl.cell(0, 1).text == "Header"  # 0.5.0+
```

Cell `.text` setter writes a single paragraph into the cell. For multi-paragraph cells, walk `cell.paragraphs` and call `add_paragraph()` on the cell directly.

## What's new in 0.5.0 — additions you can rely on

These all match upstream python-docx 1.x exactly, no Athena-specific deviations:

| Surface | Where |
|---|---|
| `Document.iter_inner_content()` → yields `Paragraph \| Table` in document order | walking mixed block content |
| `Paragraph.iter_inner_content()` → yields `Run \| Hyperlink` | walking inlines (skips empty runs) |
| `Run.iter_inner_content()` → yields `str` text segments (and `\\f` page-break markers) | rich-content traversal |
| `Section.even_page_header` / `Section.even_page_footer` | even-page header/footer access |
| `Table.row_cells(row_idx)` / `Table.column_cells(col_idx)` / `Table.table` | symmetric python-docx accessors |
| `WD_UNDERLINE.INHERITED` (= -1) | underline-inheritance sentinel |
| `add_heading(text, level=N)` accepts `N=0..9` | Title + Heading 1-9 (was 1-6); levels 7-9 clamp to 6 server-side since SuperDoc maxes at 6 |
| Merged-cell read aliases all positions to master | `cell(0,1).text` returns master after merge |

## Athena-specific behavior to remember

```python
with Document.create(...) as doc:    # recommended — autosaves + closes on clean exit
    doc.add_paragraph("…")

doc.save("ignored.docx")  # required arg matches python-docx; the path is unused
doc.close()               # disposes the session + buffer + HttpClient; idempotent

# In the Daytona sandbox prelude or any long-running process:
import docx
docx.flush_all()           # drains every open Document's CommandBuffer
```

There is **no user-facing batch context** in the docx SDK — every primitive looks like one synchronous Python call. Under the hood, `CommandBuffer` already coalesces consecutive pure-mutation setters into a single HTTP POST on a 100ms idle window. Queries (`paragraphs`, `tables`, `iter_inner_content`, `cell.text`) and response-bearing creates (`add_paragraph`, `add_heading`, `add_table`, `add_picture`) flush the buffer eagerly so the result you read reflects every preceding mutation.

## Errors

Catch `docx.errors.DocxError` for everything from this SDK. Subclasses:

```python
from docx.errors import (
    DocxError,                # base
    SessionError,             # any session-open or -use failure
    AuthenticationError,      # bad / expired Athena API key, or 401/403 from docx-studio
    UnsupportedProviderError, # asset is on ysweet, not yhub
    DocumentClosedError,      # operating on a closed Document
    ValidationError,          # bad args, out-of-range indices
)
```

A `DocxError` with the message `docx-studio batch reported a partial failure: ...` means HTTP 207 — at least one command in your batch ran but a later one failed, and the doc state is undefined past that point. Re-read it (e.g. via `doc.iter_inner_content()`) before taking another action.
